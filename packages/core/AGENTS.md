# @thomasfosterau/effect-biz

The foundation every domain package builds on, and the vendor-neutral payments core every payments provider implements. Peers: `effect`, and `@thomasfosterau/effect-auth` (optional, for `./Authorization` only). No SQL; no HTTP code outside `./Payments.internal`'s `effect/http` helpers shared by the providers; no vendor SDK and no provider vocabulary; no ERP domain vocabulary (no parties, products or orders) outside the payments modules' own entities.

## Boundary

Imports nothing from this workspace. Every other package imports it through its published `exports` (so through `dist/`).

Two halves, one package:

- **The foundation** (`src/index.ts`, `.`): identifiers, tenancy context, error channel, domain events and repository conventions.
- **Payments** (`src/Payments*.ts`, `./Payments` and `./Payments.<Name>`): the neutral capabilities, entities, `Money`, `Page`, `IdempotencyKey`, `Stub` and the `PaymentsError` channel, moved here from effect-finance's `@thomasfosterau/effect-payments`. `./Payments` is the barrel (what `@thomasfosterau/effect-payments` used to export); each `Payments.<Name>` is one module of it. The root `.` entry does not re-export payments. The payments `Customer`, `Product` and `Price` are the provider's records (a Stripe customer, a billing plan), not the ERP's parties or catalogue; a domain package maps between the two.

## Invariants

- **The foundation is one subpath per module** (`./Id`, `./BizError`, …); `src/index.ts` (`.`) still carries only `name`, and the remaining platform-foundation slices (domain events and the outbox, #30) add their own subpaths. `./testing` (`src/testing.ts`) is a flat module too, since `vite.package.ts` derives each pack entry `src/<key>.ts` from its `exports` key; it is the contract kit, not an internal.
- **Ids are lower-case UUIDv7 strings, branded per kind** (`Id.make("PartyId")`), and come only from the `IdGenerator` service, never from `crypto.randomUUID` or a host's own identifiers. `Id.layer` keeps them increasing within a millisecond with a 12-bit counter (RFC 9562 method 1), seeded below half its range so a burst of 2,048 ids fits one millisecond before the timestamp is borrowed forward.
- **Errors come from `BizError`.** A domain package adds its own tagged error only for a case a caller must branch on; any other broken rule is a `BusinessRuleViolation` with a module-namespaced `code`. No error field or message carries a secret or personal data: only entity kinds, ids, codes and schema paths, and each message is built from those fields (a `message` getter). `BizError.httpStatus` is the one mapping the HTTP surfaces use; a new error adds its row there, to `isRetryable` if retryable, and to the HTTP table in [`docs/core/ids-and-errors.md`](../../docs/core/ids-and-errors.md).
- **Every repository call runs under a tenant.** `Tenancy.TenantContext` is a requirement of every repository method (in `R`, so a call without it does not compile); a repository reads and writes only that tenant's rows, so another tenant's entity is `NotFound`, never `Forbidden`. `TenantContext`, `CompanyContext` and `Actor.CurrentActor` are request-scoped and carry `@effect-leakable-service`, the `@effect/tsgo` tag that lets them appear in a service's method requirements; nothing else does. Tenancy is independent of effect-auth's Organizations (#130).
- **Only `./Authorization` imports effect-auth.** `@thomasfosterau/effect-auth` is an optional peer: `src/Authorization.ts` is the one module that imports it (nor does `./testing`; the permissive test `Authorizer` is `Authorization.layerPermissive`), so a host without it uses every other subpath unchanged. No other module's requirements name an effect-auth service: `./Company`'s commands do not call `authorize`; a host that authorises wraps them. effect-biz has no policy engine, no RBAC and no authentication: effect-auth's `Authorizer` decides.
- **Actions are `"resource:action"`** (`"company:archive"`, kebab-case resource), declared per module with `Authorization.catalogue` and merged into the host's effect-auth `AuthorizationModel` with `Authorization.model`; a resource is an effect-auth `EntityRef` of the module's entity type (`Company::"<id>"`). A command calls `Authorization.authorize(action, resource)` before it loads.
- **A denial is `Forbidden`**, with the action, the resource as effect-auth renders it and a `DecisionTrace` (the reason and the determining policies' ids, effects and results; never the principal, an attribute value or a policy's error text). Any other `Authorizer` failure is `Unavailable` (`"Authorizer"`). `CurrentActor` is derived from effect-auth's `CurrentPrincipal` (`Authorization.withActor` / `layerActor`): a `System::"<name>"` principal is a system actor, the actor's id is the principal's id and the display name defaults to it.
- **Writes are version-guarded.** A repository's `update` takes the entity at the version it was loaded at (`entity.audit.version`) and stores it at the next one; a stale version fails with `ConcurrencyConflict`. `insert` takes version 1; `archive` / `restore` take `(id, version)`. The in-memory layers decide eagerly against the committed rows (for a precise error) and stage a guarded write (`Memory.put`: the row must still be at the decided version, 0 for an insert) that re-checks the version at commit, so of two updates from one version exactly one succeeds (#128); a SQL layer commits one version-guarded batch.
- **Every command is load → decide (pure) → commit one batch** (`./UnitOfWork`, #29, #128). The service wraps each of its commands in `UnitOfWork.transaction`, never the caller; a repository never opens a transaction. Inside one, a repository's writes are staged into the transaction's `Journal` (a `Context.Reference`, empty outside a transaction, so repository methods need nothing new in `R`), and the outermost transaction commits them as one atomic batch once the command succeeds; a command that fails or is interrupted before that applies nothing. Outside a transaction a write commits at once as a batch of one. The in-memory stores are `TxRef`s, so `UnitOfWork.layerMemory` commits a batch across every store (aggregates and logs) in one `Effect.tx`; the commit is uninterruptible.
- **No read-your-writes.** Reads inside a transaction see committed state, never the writes staged so far: a command decides from what it loaded.
- **Retry at the outermost transaction only.** A nested `transaction` joins the outer one. When the batch's guard fails at commit, nothing in it applies and the outermost transaction re-runs the whole command from its load step, with jittered exponential backoff (5 attempts from 10 ms by default, `UnitOfWork.Options`), then fails with that `ConcurrencyConflict`. A failure of the command itself, a `ConcurrencyConflict` it raises included (a stale version it was given), is never retried. `./testing`'s `unitOfWorkContract` is the suite every unit of work runs (on a live clock, since retries sleep).
- **A repository port is `Repository.Port<A, I>`** (`get`, `getMany`, `find`, `insert`, `update`, `archive`, `restore`; `Repository.Deletable` only where the domain allows a hard delete), a convention and helper type, not a base class. Every in-memory layer is built on `./Memory` and every implementation runs `./testing`'s `repositoryContract` in its suite; `./testing` imports no test runner.
- **Audit fields live on the entity, as one `audit: Audit.AuditFields` member** (`createdAt`, `createdBy`, `updatedAt`, `updatedBy`, `version`, `archivedAt`), so domain fields stay the entity's own and `Query` sees only them. Times are `DateTime.Utc` from `Clock`, encoded as ISO strings; `createdBy` / `updatedBy` are `CurrentActor` ids, never display names. A command builds a new entity's audit with `Audit.created`; the repository moves it on (`Audit.next`) in `update` / `archive` / `restore`, which therefore require `CurrentActor`, and `update` keeps the stored creation and archive fields. An entity is rebuilt with new audit through the repository's `withAudit` (`Struct.omit` plus the class constructor; never a spread of the instance).
- **Archive, not delete.** `archive` sets `audit.archivedAt`, `restore` clears it, each version-guarded and bumping the version; from the wrong state it is `InvalidTransition`. `get` sees an archived entity; `find` excludes it unless `archived: "include"` / `"only"`.
- **Paging is keyset paging in a total order**: the query's sort keys, then the id (UUIDv7, so creation order). A `Page.Cursor` is base64url JSON of the last item's sort-key values (kind-tagged, so a date-time and a decimal stay apart) and id, plus the sort's fingerprint (`Query.sortKey`); a malformed cursor or one for another sort is a `ValidationError` on `["cursor"]`. A page starts strictly after the cursor, so an insert between pages never repeats or skips a row that existed. `limit` defaults to 50, is capped at 500, and below 1 or non-integer is a `ValidationError` on `["limit"]`.
- **`Query` is small and typed over the entity's top-level fields**: `eq` / `in` on scalars (string, number, boolean, `DateTime.Utc`, `BigDecimal`), `range` on the ordered ones, `search` (a case-insensitive substring of the repository's `searchable` fields in memory; full-text in SQL), `archived` and `sort`. `Query.run` is the one pure interpreter; a SQL layer translates the same spec and must agree with it (the contract suite checks the common cases).
- **No `number` for an amount, quantity, price or rate.** They are `effect/BigDecimal` values (`./Decimal`), encoded as canonical decimal strings: `-?digits` with an optional `.digits`, never an exponent and never a JSON number (`BigDecimal.format` alone would emit an exponent at |scale| >= 16, so `Decimal` encodes with its own plain formatter). Add, subtract and multiply are exact and stay Effect's own; nothing here re-implements `BigDecimal`.
- **Nothing rounds without a policy.** Every function that discards digits (`Decimal.divide`, `Percentage.of`, `Rate.apply` / `invert`, `Money.round`) takes a `RoundingPolicy`; `Money.round` alone has a default (the currency's minor units, half-even), and `Money.multiply` never rounds. Common names map onto Effect's modes: half-up is `"half-from-zero"`, up is `"from-zero"`, down is `"to-zero"`.
- **Pure failures are a `Result` of a `BusinessRuleViolation`, never a throw.** `core.unit-mismatch` (`Quantity.add` / `subtract`, `left` and `right` in `details`, an `Option` of the record), `core.currency-mismatch` (`Money.add` / `subtract` / `sum`), `core.money-scale` (`Money.toMinorUnits` of an amount finer than the minor unit), `core.invalid-allocation` (`Money.allocate` with a negative or all-zero ratio) and `core.rate-not-positive` (`Rate.make` / `invert`). Only the literal helpers `Decimal.make` and `Currency.make` throw, for code literals.
- **One minor-unit table.** `Currency.minorUnits` is the ISO 4217 exponent table; `Money` reads it. `Payments.internal.exponentFrom` stays parameterised by each provider's own tables (the payments `Money` is a different type: integer minor units in a `number`, converting at the gateway edge through `Money.toMinorUnits` / `fromMinorUnits`).
- **Units are codes.** `Quantity` carries a `UnitCode` and nothing else; the catalogue owns units and conversions. `Money.Order` compares amounts only, so check currencies match first.

### Payments

- **Amounts are minor units everywhere in the core.** Major-unit conversion (a vendor's decimal strings or numbers) happens inside the provider.
- **A new enumeration is lenient from the start.** Declare `Known<Name> = Schema.Literals([...])`, export `<Name> = Enumeration.lenient(Known<Name>)`, and have every provider produce `Other` for a value it cannot map; never add a closed `Schema.Literals` to an entity field a provider fills from a response. Request-only inputs (a filter, `CheckoutMode`) stay closed.
- **Hosted sessions never take an amount.** `CheckoutSession.create` names price ids; what the buyer pays is the provider's price. Both hosted capabilities return an entity whose `url` is required, so a provider answering without one fails rather than inventing a redirect.
- **`idempotencyKey` only where every implementing provider can honour it.** It is on `Customer.create`, `Product.create`, `Price.create`, `PaymentIntent.create` / `confirm`, `Subscription.create`, `Refund.create` and `CheckoutSession.create`, and deliberately not on updates (set-semantics), `Subscription.cancel` / `PaymentIntent.cancel` (not every provider can honour a key there; PayPal, a former provider, could not) or `BillingPortal.create`; `tests/Payments.IdempotencyKey.test.ts` pins that at the type level. A provider maps it to its vendor mechanism and never accepts a key it would silently drop; it calls `IdempotencyKey.validate` first, so a raw string fails with `PaymentInvalidRequestError` before any request. A new create / confirm operation gets the option only after checking every provider that implements it. The replay window is a documentation contract ("a few hours"), not a type (the guide `docs/core/retrying-writes.md` has the table); Stripe's limit and window are unverified (effect-finance#93).
- **Adding a capability** means a new `Payments.<Name>.ts` module here, a new `exports` entry, and an implementation or an explicit unsupported failure in every provider. A new capability also gets a constructor in `Payments.Stub.ts` and a place in `Stub.layer`. A provider without the capability exports a stub layer (built with `Stub`) failing with `PaymentInvalidRequestError` ("<Provider> does not support …", the same failure as an unsupported operation) and leaves it out of its `capabilities` bundle, so the gap still shows at compile time by default.
- **`./Payments.internal` is the one semver-exempt subpath.** `src/Payments.internal.ts` (`@thomasfosterau/effect-biz/Payments.internal`, a single `exports` entry) holds what the providers share because they may import only this package (of this workspace): `shareLogin`; the vendor-neutral integer money core (`exponentFrom` over two `HashSet` tables, `scaleToMinor`, `parseDecimal`, `decimalText`, `formatDecimal`, `checkMinorUnits`); the token-login plumbing for a provider that logs in for an access token (`tokenCache`, `send`, `networkError`, `timedOut`, `timeoutOf`, `isAbsoluteHttpUrl`, `isOk`); the request helpers for a provider over Distilled (`omitUndefined`, `checkId`, `stringField`, `observeResponses`, `rejectedError`); the response handling for a provider over a plain JSON API (`responseDecoder`, `epochSecondsOf`, and `errorFromStatus`, the status-wins classification of an HTTP error); and the paging of a page-numbered list (`pageNumberedList`). It is documented as internal in `docs/core/internal.md` and in its doc comments, and no application imports it. Everything in it takes a fraction-digit count, a provider name, an `effect/http` value or a plain callback, and names no vendor and no client library: the per-currency exponent tables, the wire adapters (a vendor's decimal strings or JSON numbers), the login requests, the wire schemas, the status spellings, the reading of each vendor's error body and everything typed by Distilled (its `Credentials`, `Retry` and `ResponseValidation` services, the outcome classification) stay in each provider. A helper two providers duplicate moves here; one a single provider uses stays there. Since the PayPal and Airwallex providers were dropped (2026-11-06), Stripe is the only consumer, and the money core, the token-login plumbing, the plain-JSON response handling and `pageNumberedList` have none in this repository; they stay for the next provider, and `tests/Payments.internal.test.ts` keeps covering them. `tests/Payments.internal.test.ts` is the only suite for these helpers.
- **One login at a time, and a 401 forgets the token.** `shareLogin(cached, login)` (`Payments.internal.ts`) builds a provider's `getToken`: the first caller without a usable token runs the login and publishes its outcome through a `Deferred`, and callers arriving meanwhile await that same outcome (token or error, effect-finance#65). The slot is cleared before the outcome is published, so the next call after a failure logs in afresh, and if the caller running the login is interrupted the waiters retry rather than being stranded. A login that fails on its own is shared, never retried by its waiters. The 401 half is the provider's: a 401 on a resource request clears the cached token, only if it is still the token that request used, so the next call logs in again.
- **Every exchange is time-boxed.** A provider bounds its login by `loginTimeout` and each resource request by `timeout`, both covering the response body too. A timeout interrupts the fetch (aborting it) and fails with `PaymentNetworkError`; for the login, every caller waiting on it fails with that same error after one `loginTimeout` instead of stalling behind a hung handshake (effect-finance#54, effect-finance#65). `timeout` excludes token acquisition. A timed-out non-GET has an unknown outcome, which a caller makes safe to retry with the provider's request id. A timeout is positive and finite, or `Infinity` for none; anything else is a `PaymentConfigError` from `make`. The defaults are the provider's.

## Terms

- **Capability** — one `Context.Service` per resource family (`Customers`, `Products`, `Prices`, `PaymentIntents`, `Subscriptions`, `Refunds`, `CheckoutSessions`, `BillingPortalSessions`), with module-level accessors (`Customer.create`, …). A provider supplies a `Layer` per capability; a program depends only on the capabilities it uses, so a provider may implement a subset.
- **Neutral entity** — a `Schema.Class` (`Customer`, `Product`, `Price`, …) in camelCase with amounts in **minor units** (`Money.amount` in cents for USD). A provider maps its own shape onto it.
- **Lenient enumeration** — every neutral status or type (`PaymentStatus`, `SubscriptionStatus`, `RefundStatus`, `PriceType`, `RecurringInterval`) is `Known | Other` (`Payments.Enumeration.ts`): the known literals stay bare strings (`"succeeded"`), and `Other` is the one shared tagged catch-all `{ _tag: "Other", raw: string }` for a provider value the library does not model. Each enumeration exports its literals as `Known<Name>` (the type to use for request filters and params, which can only name a known value) and the lenient union as `<Name>` (the type of the entity field). A provider decoder never fails on an unrecognised enumeration value, and one such value never fails a list page: Stripe's wire schemas use `Enumeration.fromWire(Known<Name>)`; a provider that maps its own spellings does so with a `to*Status` that returns `Enumeration.other(raw)` from its fallback (`Match.orElse`). An exhaustive match over an entity field must handle `Other` with `Enumeration.isOther` (a bare `value._tag` check does not type-check against the plain-string known members).
- **Page** — `Page<A>`, the one pagination shape (`data`, `hasMore`, and `nextCursor`, an `Option` that is `Some` when there is more: an opaque cursor the caller passes back as the list params' `startingAfter`, with the same `limit` and filters, owner decision on effect-finance#202). A provider whose vendor pages by cursor sets it to the last item's id (Stripe, which also takes any item id); a page-numbered one lists through `pageNumberedList`, which encodes the next page number and the `limit` and reads them back, refusing an item id or a cursor for another `limit`. `Deleted` for `del` results.
- **Error channel** — `PaymentsError`, the union of the `Schema.TaggedError` classes in `Payments.PaymentsError.ts` (`PaymentProviderError`, `PaymentAuthenticationError`, `PaymentRateLimitError`, `PaymentInvalidRequestError`, `PaymentNetworkError`, `PaymentsUnavailable`, plus `PaymentConfigError` and `SignatureVerificationError`, which are outside the union). Every capability method fails with it and nothing else.
- **"Not configured ≡ down"** — `PaymentsUnavailable`: no provider can serve the call, typically because its credential is absent. Raised at call time, never while a layer is built, so an application without payments configured still starts; it looks to the program exactly like a provider outage (an HTTP API answers it with a 503).
- **Idempotency key** — `Payments.IdempotencyKey.ts`: a branded `Schema` (1 to 64 characters of `A-Za-z0-9_-`), `generate`, `validate`; the caller-facing contract (one key per logical write, which errors to retry) is that module's doc comment and the guide `docs/core/retrying-writes.md`.
- **Stub** — `Payments.Stub.ts`: capability layers whose every call fails with one given `Effect` (`Stub.layer`, one constructor per capability, `Stub.unavailable`). Providers build their unsupported-capability layers from it.
