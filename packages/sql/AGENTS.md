# @thomasfosterau/effect-biz-sql

The SQL foundation every domain package's `effect/sql` repository layer builds on: the `Dialect` service, the column codecs, the SQL unit of work (`./SqlUnitOfWork`) and the repository helper (`./SqlRepository`), on Postgres, SQLite and Cloudflare D1, with in-process test databases. Peers: `effect` (`SqlClient` lives in it, `effect/sql`: there is no separate `@effect/sql` package), and the optional `@effect/sql-sqlite-node` and `@effect/sql-pg` (for `./testing` and `./testing.postgres` only). The guides are [`docs/sql/columns-and-dialects.md`](../../docs/sql/columns-and-dialects.md) and [`docs/sql/repositories-and-unit-of-work.md`](../../docs/sql/repositories-and-unit-of-work.md).

## Boundary

Imports only core (`@thomasfosterau/effect-biz`, through its published `exports`, so its `dist/`); core never imports this package (`.fallowrc.json`'s `sql` zone). No ERP domain vocabulary: no table here names a party, an order or a ledger. A domain package's SQL layer imports this package; this package imports no domain package.

Planned here, each its own slice: the migrator (#37), tenant scoping (#38), and the SQL outbox, inbox and sequences (#40). The unit of work and repository helpers over SQL (#39) are `./SqlUnitOfWork` and `./SqlRepository`.

## Invariants

- **Private until the owner publishes it.** `package.json` has `"private": true`, so Changesets (`privatePackages.version: false`) neither versions nor publishes the package and it carries no changeset. Never remove `private` or add a changeset for it in a feature PR: that is the owner's step once its npm bootstrap and trusted publisher exist ([PUBLISHING.md → A new package](../../PUBLISHING.md#a-new-package)).
- **Every layer requires only `SqlClient.SqlClient` and `Dialect.Dialect`**, plus what this package itself defines: `SqlUnitOfWork.Committer` (from `SqlUnitOfWork.layer`, which a repository captures when built) and, on D1, the `SqlUnitOfWork.Batch` port the host fills from its D1 client. No module but `./testing` (SQLite) and `./testing.postgres` (Postgres) imports a client package, so the main entry points work with whichever client the host provides (D1, libSQL, PGlite, …) and an optional peer is needed only for the testing subpath that names it.
- **The dialect is derived, not configured.** `Dialect.layer` reads the client's statement compiler (`pg` → `postgres`, `sqlite` → `sqlite`) and its `driver` (`"d1"` → `d1`); any other compiler is `UnsupportedDialect`, raised while the layer is built. `Dialect.layerAs` states the dialect only for a client that reports no `driver` (effect before 4.0.6). The `effect` peer stays `^4.0.0`: below 4.0.6 D1 reads as `sqlite`, which `layerAs("d1")` corrects.
- **One statement shape for every dialect.** Commands are load → decide → one atomic batch of version-guarded writes (#128), so nothing relies on row locks, `SELECT … FOR UPDATE`, savepoints or an interactive transaction, which D1 lacks. `Dialect.match` branches only where the SQL text differs (a JSON operator, a column type).
- **Column conventions.** snake_case column names, mapped to the entity's camelCase fields with `Schema.encodeKeys` in the row schema, or by `SqlRepository.make`'s column map (the field in snake_case unless `columns` names it) (never the client's `transformResultNames`, which is the host's); `tenant_id` on every business table and `company_id` on every company-owned one; `version` plus the audit columns `created_at`, `created_by`, `updated_at`, `updated_by`, `archived_at`, matching core's `Audit.AuditFields`; the id (a UUIDv7 from core's `IdGenerator`) is the primary key.
- **Column types per dialect** (`Dialect.Info`): ids `uuid` / `text`; decimals `numeric` / `text` (never `REAL`, `double precision` or a SQLite `NUMERIC` affinity); instants `timestamptz` / ISO-8601 text; JSON `jsonb` / text.
- **A row crosses the boundary through `Schema`.** A SQL layer decodes every row with a schema built from `./Column` (through `SqlSchema`) and encodes every written value the same way; it never reads a column as a bare `unknown`.
- **The codecs** (`./Column`): `decimal` is core's `Decimal` (canonical decimal text on every dialect; a JavaScript `number` never reaches a monetary column); `timestamp` is `DateTimeUtcFromDate` on Postgres (the client returns and binds `timestamptz` as a `Date`) and `DateTimeUtcFromString` elsewhere; `json(schema)` goes through `Schema.toCodecJson(schema)`, as JSON text on SQLite / D1 and, on Postgres, reading the parsed `jsonb` and writing JSON text (bound untyped, so Postgres parses it into the column); `id` is core's `Id.make`; `nullable` is `Schema.OptionFromNullOr` (`None` is SQL `NULL`).
- **A commit is one atomic batch of guarded statements, never an interactive transaction** (#128, #39). `SqlUnitOfWork.layer` builds core's `UnitOfWork.make` (which owns retry, nesting and interruption) over a journal of `Write`s: a statement plus, for a version-guarded one, its `Guard` (the rows it must write, and the conflict to fail with, read after the rollback). A guarded statement writes nothing when its guard does not hold and returns one row per row it writes (`RETURNING id`). Postgres and SQLite run the batch in one `withTransaction`, counting each guarded statement's returned rows; D1 runs it as one `Batch`, each guarded write followed by a guard statement that raises when unmet (`CASE WHEN changes() = n THEN 1 ELSE json_extract('{}', '$effect-biz-guard:<index>') END`), whose error message names the write. `layer` on D1 without a `Batch` fails with `BatchRequired` while built. No savepoints: a nested transaction joins the outer one. A `SqlError` is a defect (core's commit and port have no channel for one); so is a stored row that does not decode.
- **A SQL repository is `SqlRepository.make`, or follows it.** Every read filters by the `TenantContext`'s `tenant_id` and decodes through `Schema` (never a cast); every write decides eagerly against a fresh read for its precise error (`AlreadyExists`, `NotFound`, `ConcurrencyConflict`, `InvalidTransition`), stamps the audit fields with `Audit.next` as `Memory.repository` does, and stages one guarded statement: `INSERT … ON CONFLICT (id) DO NOTHING RETURNING id`, or `UPDATE … SET …, version = version + 1 WHERE tenant_id = ? AND id = ? AND version = ? RETURNING id`.
- **`find` agrees with `Query.run` and shares its cursors.** Only the `filterable` allow-list (each field with its `Kind`; the id always) may be filtered or sorted, else `ValidationError`; values bind through the field's codec. Text orders by code point (`COLLATE "C"` on Postgres), a SQLite / D1 decimal compares as `REAL` in a range or sort (exact in `eq` / `in`), `search` is `ILIKE` on Postgres and `lower(…) LIKE` elsewhere with the needle's wildcards escaped. Paging is keyset in the expanded `OR` form, then the id; cursors are `Page.encodeCursor` / `decodeCursor` against `Query.sortKey`, so memory and SQL cursors are interchangeable. The suites check every case against `Query.run`, page by page.
- **Tests are hermetic.** Unit suites run on `Testing.layerSqlite` (a fresh `:memory:` database per build, on `node:sqlite`, so no native build); the Postgres suites (`tests/*.postgres.test.ts`) fall back to SQLite and skip their cases unless `EFFECT_BIZ_PG_URL` is set (the opt-in CI job is #21). Every codec round-trips the sample table (`tests/sample.ts`) on both. The sample repository (`tests/widgets.ts`) passes core's repository and unit-of-work contracts and `tests/suite.ts` on SQLite, on D1's batch commit run on SQLite (`Testing.layerBatch`: D1 has no in-process database, and its SQL is SQLite's) and on Postgres; core's `Company` passes the repository contract on SQLite. Each suite creates its own tables (the migrator is #37).

## Terms

- **Dialect** — `postgres`, `sqlite` or `d1`: the `Dialect.Dialect` service's `Info` (`name`, the column types, `interactiveTransactions`, `rowLocks`).
- **Driver** — `SqlClient.driver`, the client package's name without `@effect/sql-` (`"pg"`, `"sqlite-node"`, `"d1"`); it tells D1 apart from other SQLite clients, which share a compiler.
- **Column codec** — a `Schema` from `./Column` whose Type is the domain value and whose Encoded form is what the dialect's driver binds and returns.
- **Business table** — a table holding a domain package's entities: it carries `tenant_id`, `version` and the audit columns.
- **Write / guard** — a statement staged into the unit of work's journal, and the rows it must write for the batch to commit (`SqlUnitOfWork.guarded`; `unguarded` for an append).
- **Guard statement** — on D1, the `SELECT` after a guarded write that raises (a bad JSON path naming the write) unless `changes()` is the guard's rows, aborting the batch.
- **Allow-list** — `SqlRepository.make`'s `filterable`: the fields `find` may filter and sort by, with each one's `Kind` (`text`, `id`, `number`, `boolean`, `timestamp`, `decimal`).
