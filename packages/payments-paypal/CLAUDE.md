# @thomasfosterau/effect-biz-payments-paypal

PayPal REST: `Products`, `Prices` (billing plans), `PaymentIntents` (orders), `Subscriptions` and `Refunds`, as `Layer`s (`PayPalPayments`) over Distilled's generated PayPal operations (`@distilled.cloud/paypal`, effect-finance#146). There is no REST client of the package's own: `./PayPal` (`PayPalClient`) was removed in effect-finance#146 (owner decision, 2026-10-09), and a program needing a call the capabilities do not cover uses `@distilled.cloud/paypal` directly with its own token. The public config types (`PayPalConfig`, `PayPalEnvironment`) live in `PayPalPayments.ts`, which `layer` takes. Peer: `effect` at `^4.0.0` (`catalogs.peers`, which is also Distilled's own peer range). Dependencies: the core, `@distilled.cloud/paypal` and `@distilled.cloud/core` (both pinned exactly in the catalog, at the same version as the Stripe package's). Requires `HttpClient` (`effect/http`).

## Boundary

Imports only `@thomasfosterau/effect-biz` (its `./Payments` and `./Payments.<Name>` subpaths) from this workspace. Distilled is imported only by `PayPalPayments.ts` and `internal/distilled.ts`, and only through its subpaths (`@distilled.cloud/paypal/<service>` for the operations, `/Credentials`, `/Protocol`, `/Retry`, `@distilled.cloud/core/response-validation`); a public declaration names `@distilled.cloud/paypal/Credentials` and nothing else of Distilled's (`tests/dist-consumer/src/distilledDeclarations.ts`), so a consumer never type-checks the generated service modules (Orders alone is a 0.8 MB declaration).

## Invariants

- **Every call goes through `HttpClient`**, never `globalThis.fetch`: the layers require `HttpClient.HttpClient`, so a consumer provides `FetchHttpClient.layer` and a test stubs `FetchHttpClient.Fetch` (`tests/support.ts`'s `stubPayPal` for the capability layers). Every body is decoded with `Schema`: token and error bodies in the session and the Distilled client, resource bodies in the capability layers — the Distilled client's `call` returns `unknown`, and each layer pipes it through a `decode*` from `internal/mapping.ts` (a wire `Schema` narrowed to the fields the mapping reads), so a 2xx that does not decode fails with `PaymentProviderError`.
- **The capability layers run on Distilled under the package's request policy** (`internal/distilled.ts`, `tests/PayPalPayments.wire.test.ts`): the access token comes from the session's login and cache (never Distilled's `CredentialsFromEnv`, which reads `process.env`), fed to Distilled's `Credentials` with the session's base URL on every call; `Content-Type` and `Accept: application/json` on every request (Distilled sends no content type on a bodyless `POST`); Distilled's retries switched off (no request is ever repeated by this package); Distilled's `ResponseValidation` pinned to lenient, because its schemas mark nested members required (a billing cycle's `sequence`, a link's `href`, `billing_info.outstanding_balance`, …) that the mapping never reads, and the response decoders decide what is malformed; a per-request timeout. Distilled's error classes keep neither the status nor the whole body, so the client watches each response through the `HttpClient` it hands Distilled and classifies a non-2xx with `handlePayPalError` (the wire test checks it against the session's own `send` + `handlePayPalError` reading, the mapping the removed `PayPalClient` applied); a Distilled failure with no response behind it is a `PaymentNetworkError` (an `HttpClientError`) or a `PaymentProviderError` coded by its tag. Distilled's schemas come from PayPal's OpenAPI specifications as mirrored by `distilled-mirror/spec-mirror-paypal`, whose four files this package uses are identical to the `paypal/paypal-rest-api-specifications` commit `90e8041` the README pins (Orders 2.32, Catalog Products 1.0, Subscriptions 1.8, Payments 2.12); on a Distilled bump, re-check that and the fields `internal/mapping.ts` reads.
- **The capabilities need a `process` global** (on Workers, `nodejs_compat`; owner decision on effect-finance#146: document it, no shim). Distilled reads `process.env.DISTILLED_DEBUG_HTTP` unguarded each time it encodes a request or decodes a response (effect-finance#148). Building a layer and logging in never reach Distilled.
- **Top-level layer constructions in `PayPalPayments.ts` are `/* @__PURE__ */`, and the capability modules are namespace imports by subpath**, so a bundler drops the capabilities (and the Distilled operations, with their schemas) a program does not use. The same holds for `internal/mapping.ts`: every top-level wire schema and decoder is a `/* @__PURE__ */` call, nested calls included, over `import * as Schema from "effect/Schema"` and the core's modules by subpath (a named `{ Schema }` import from `effect` keeps every schema), so one capability's decoders never stay in a bundle that imports another (effect-finance#149). Statuses decode as strings; the `to*Status` functions map a recognised one onto the neutral literal and an unrecognised one onto `Enumeration.Other` carrying the raw string (never a silent neutral fallback, never a decode failure).
- **Login sharing and timeouts:** see `packages/core/CLAUDE.md` (`shareLogin`, "One login at a time", "Every exchange is time-boxed"). Provider-specific: the session (`internal/auth.ts`, used by the Distilled client; its cases are in `tests/PayPalPayments.session.test.ts`) holds `token = shareLogin(cache.cached, login)` over the core's `tokenCache`; a 401 on a resource request clears the cached token, only if it is still the token that request used (`Session.forget`, the cache's `forget`); `loginTimeout` defaults to 30 s and `timeout` to 80 s (the Stripe client's per-attempt default); a caller makes a timed-out write safe to retry with the neutral `idempotencyKey` (below).
- **The neutral `idempotencyKey` is the `PayPal-Request-Id` header, `POST` only.** One key per logical write, created by the caller before the first attempt and reused by every retry (the package never generates one, and never retries). The capability layers pass the `idempotencyKey` of a create / confirm through `IdempotencyKey.validate` into the Distilled operation's `payPalRequestId`, on six `POST`s (order create and capture, product, plan and subscription create, capture refund); with no key none is sent (a random one would deduplicate nothing, since a caller's retry re-runs the layer). The calls whose endpoint ignores the header (plan activate / deactivate, subscription cancel) take no key: a header PayPal ignores would leave the caller believing a retry is safe. Length and retention are per API, from PayPal's OpenAPI specifications (the README's `PayPal-Request-Id` note has the table and the pinned sources): Orders 1–108 characters and 6 hours by default, Catalog Products and Subscriptions no stated length and 72 hours, Payments refunds 1–10 000 characters and no stated retention.
- **`Content-Type: application/json` on every request**, body or not (PayPal answers a bodyless POST without it with 415).
- **Configuration from the environment is read through `Config`** in `layerFromEnv`, and a missing or empty variable still fails with `PaymentConfigError`. Effect rc.118's `ConfigProvider` treats a literal empty string as a missing value, so an empty variable is the same as an unset one: an empty id or secret fails with `PaymentConfigError`, and an empty `PAYPAL_BASE_URL` falls back to the `PAYPAL_ENV` endpoint. A provider built with `preserveEmptyStrings: true` restores the old reading, which is the safer one for `PAYPAL_BASE_URL`: a blank stays `""` and the session refuses it with `PaymentConfigError` (a `baseUrl` must be an absolute http(s) URL), instead of silently selecting an environment's endpoint.
- **`PAYPAL_ENV` is required** (`live` | `sandbox`, read with `Config.Literals`): `layerFromEnv` never selects live by default (effect-finance#90). It maps onto `PayPalConfig.environment` (`live` → `https://api-m.paypal.com`, `sandbox` → `https://api-m.sandbox.paypal.com`); `baseUrl` / `PAYPAL_BASE_URL`, when set, wins. In `layer`, `environment` is optional and defaults to `live`.
- **No `Customers`.** PayPal has no first-class customer resource; the provider deliberately implements a subset of the core's capabilities, and a program needing `Customers` fails to type-check against this layer.
- **Money crosses the boundary as major-unit decimal strings** (`internal/money.ts`); the core stays in minor units. Conversion is integer arithmetic, never a float, and the per-currency exponent follows PayPal's currency-codes reference (HUF, JPY, TWD zero-decimal), not Stripe's list. The response decoders reject an amount with excess decimals rather than round it. Request amounts must be non-negative safe integers and fail with `PaymentInvalidRequestError` before any request.
- **Vendor error bodies become neutral errors in `internal/error.ts`.** The client secret and the bearer token never appear in one: the client secret is `Redacted<string>` in the config (read with `Config.Redacted` in `layerFromEnv`) and unwrapped only where the login request is built, the token is a `Redacted` in Distilled's `Credentials` until Distilled sets the header, and a transport failure keeps only the underlying cause — never the `HttpClientError`, whose request carries the credential headers. `tests/PayPalPayments.wire.test.ts` walks every error's own-property graph for the token and the secret, because Effect's `Headers` redaction hides them from `JSON.stringify` and `String`.
- **Distilled input types declare bare `?: T`**, so an input assembled from optional neutral parameters goes through `omitUndefined` (`@thomasfosterau/effect-biz/Payments.internal`, shared with Stripe); a path id is refused (`checkId`, same place) with `PaymentInvalidRequestError` (`param: "id"`) unless it is a non-empty string, before anything is sent.

## Terms

- **Session** — `internal/auth.ts`: a validated `PayPalConfig`'s base URL and timeout plus the OAuth client-credentials login, whose access token is cached in a `Ref` and refreshed a minute before expiry (`sessionOf`), and the `Config` reading of `layerFromEnv` (`configFromEnv`: `PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET`, required `PAYPAL_ENV`, optional `PAYPAL_BASE_URL` override).
- **Distilled client** — `internal/distilled.ts`: the internal `DistilledClient` service the capability layers are built over, whose `call(operation, input)` runs one Distilled operation under the policy above. Built from Distilled's `Credentials` in context (`layerFromContext`: the token sent as it is, no login, a 401 changes nothing) or from a session (`layer` / `layerFromEnv`).
- **Capability layers** — `PayPalPayments.*Layer` and `capabilities` (over Distilled's `Credentials` and an `HttpClient`), `layer` / `layerFromEnv` (the session's login; need an `HttpClient`).
